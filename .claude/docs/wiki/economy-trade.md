# 토픽: 교역 경제

> `js/state.js` (규칙) + `js/data.js: GOODS/CITIES/SHIPS` (수치) + `js/scenes/port.js` (UI) — 시세 형성, 매매, 항구 서비스, 바람·해류. (2026-08-13)

## 설계 의도

대항해시대류의 핵심 재미는 **"어디서 사서 어디에 파는가"를 플레이어가 발견하는 것**이다. 그래서:

- 도시마다 **산지(싸다) / 수요지(비싸다)** 를 명시하고 UI에 태그로 노출한다. 숨기지 않는다.
- 대신 **어떤 항로가 이득인지는 직접 계산**해야 한다 — 거리(=일수=유지비)와 차익을 저울질.
- 시세에 노이즈를 넣어 "항상 같은 왕복"이 최적해가 되지 않게 한다.

## 시세 공식

```js
cityMul = 1 + (supply|demand − 1) × SPREAD        // SPREAD = 0.62
price   = base × cityMul × (0.86 + wobble×0.30)   // 최종 ±15%
        × shockFactor(city, good)                  // 사건이 걸려 있으면 (0.45 ~ 2.6)
```

| 항 | 의미 |
|---|---|
| `base` | 품목 기준가. 곡물 20 ~ 금괴 520 (`GOODS`) |
| `cityMul` | `city.supply[id]`(0.46~0.76) 또는 `city.demand[id]`(1.18~1.52), 없으면 1 |
| `SPREAD` | 차익 폭을 1 쪽으로 조이는 한 계수. 도시 데이터는 그대로 두고 여기서만 폭을 조절한다 |
| `wobble` | `FNV-1a(cityId\|goodId\|floor(day/3))` → 0~1 |

**`wobble`이 해시인 이유:** 같은 날 항구를 나갔다 들어와도 값이 변하면 안 된다(재입장 스캠 방지). 날짜를 3으로 나눠 **3일마다** 갱신된다.
시세는 `advanceDays()`에서 `refreshPrices()`로 전 도시가 한꺼번에 다시 계산된다.

**`SPREAD`가 있는 이유:** 원래 배율(2.4~3.3배)로는 한 항차에 자산이 배로 불어나 "여러 번 무역해야 다음 배"가
성립하지 않았다. 도시를 추가할 때마다 균형을 다시 잡지 않아도 되게 **한 계수로 전체 폭만** 조인다.

## 시장 충격 — 큰돈은 확률이 아니라 사건에서 나온다

`wobble`은 노이즈라 아무리 겹쳐도 ×1.5를 못 넘는다. 그런데 사료가 말하는 대박 항차는
그보다 크고 성격도 다르다 — **확률적 잭팟이 아니라 사건**이었다(기근·전쟁·경쟁 선단 전손·독점 붕괴).
그래서 값이 뛰는 자리를 따로 뒀다. → 근거 [research-voyage-returns.md](research-voyage-returns.md) §4-4

```js
state.shocks = [{ city, good, mult, until, why }]     // 날이 차면 걷힌다
shockFactor(city, good) = clamp(Π mult, SHOCK.floor 0.45, SHOCK.cap 2.6)
```

| 사건 | 배율 | 기간 | 하루 확률 | 어디에 |
|---|---|---|---|---|
| **기근** | ×2.0 | 20일 | 1.0% | 곡물을 **사들이는** 도시 |
| **봉쇄** | ×1.7 | 14일 | 0.8% | 곡물·무기·와인·기름 수요지 |
| **풍작·독점 붕괴** | **×0.62** | 16일 | 0.9% | 아무 산지 |
| **NPC 나포** | ×1.55 | 12일 | — | 털린 상인이 **대던** 항구 |

- **값이 내려가는 사건을 함께 둔 것이 핵심이다.** 오르기만 하면 "기다렸다 팔면 된다"가 되어
  판단이 사라진다. 풍작은 "싸게 살 기회"라 소식을 듣고 달려가는 재미가 생긴다.
- **기근은 산지가 아니라 수요지에 건다.** 산지에 걸면 살 곳이 사라져 그 항로가 통째로 죽는다 —
  콘텐츠가 주는 방향이라 하지 않는다.
- **후보 도시·품목은 매번 `CITIES`에서 만든다.** 목록을 하드코딩하면 도시를 늘릴 때마다
  거기도 고쳐야 하고 결국 안 고친다. 지금 구조는 **콘텐츠를 늘리면 사건도 저절로 는다.**
- 정본 `data.js: SHOCK.events` · 판정 `state.js: shockFactor/addShock/rollShockEvents` ·
  나포 배선 `world.js: raids()` · 화면 지도 씬 "뱃사람들의 소문".

## 화물을 잃는 사건 — 보험이 실제로 무는 것

전에는 `INSURANCE_RATE`로 보험료를 걷기만 하고 **보상하는 사건이 하나도 없었다.**
그건 보험이 아니라 세금이다. 사료에서 보험이 문 것은 전손과 **투하**(jettison)였다 —
폭풍에 배를 살리려 짐을 바다에 던지는 것(공동해손).

| | 어디서 | 무엇을 잃나 | 보험 |
|---|---|---|---|
| **폭풍 투하** | 바다 | 실은 것의 약 40%를 **값싼 것부터** | `INSURANCE_COVER`(30%) 보상 |
| **노상강도** | 내해·육로 | 약 16%를 **값비싼 것부터** | 보상 없음 |
| **통행세** | 내해·육로 | 화물가치의 4.5%를 **금화로** | 보상 없음 |

- 보상률을 요율 계수와 같은 30%로 둔 이유: 30%만 내고 100%를 받으면 보험이 공짜 이익이 된다.
  **낸 만큼만 받는다** — 손해는 남지만 파산까지는 안 간다.
- 투하 확률은 항로 위험도에서 나온다(`JETTISON_BASE 0.22 + risk×0.035`). 그 숫자의 본래 뜻이
  **사고 확률의 시장가격**이므로 같은 값을 두 곳에 쓰는 것이 옳다.
- 강도가 값비싼 것부터 가져가는 것은 투하와 정반대다 — 선장은 비단을 먼저 던지지 않고, 강도는 고른다.
- **빈도**: 시드 20판 평균 **20항차에 1건**. 사료의 보험료 중앙값 5%와 전손률 4.7%가
  독립적으로 같은 값(≈20항차)을 가리킨다. 확인 `node tools/sim-risk.mjs`.

## 시장 깊이 — 많이 사면 비싸지고 많이 팔면 싸진다

```js
depth  = MARKET.depthPerSize(45) × city.size          // 큰 항구가 더 많이 소화한다
pressure = 그 항구·품목의 최근 거래량 (하루 지나면 ×0.68)
factor = min(0.35, 0.30 × (pressure + (n−1)/2) / depth)
매입 = 시세 × n × (1 + factor)     매각 = 시세 × n × (1 − factor)
```

- **방향과 무관하게 항상 불리한 쪽**으로 작동한다. 그래야 같은 항구에서 사고팔기를 반복하는 무한 루프가 없다.
- 압력이 **누적**되므로 나눠 팔아도 피하지 못하고, 날이 지나면 회복한다.
- 이 장치가 없으면 "화물칸을 통째로 사서 통째로 판다"가 언제나 최적이라 돈이 너무 쉽게 불어난다.
- 대형선은 **큰 항구**(size 3)를 써야 값을 덜 깎인다. 품목을 섞으면 압력이 분산된다.

## 입항세

파는 쪽에만 붙는다(매입에는 안 문다). **두 겹**이다:

- `data.js: TARIFF` — 규모별 **기본율**. size 1 = 3% / 2 = 4.5% / 3 = 6%. 도시를 추가해도 저절로 정해진다.
- `data.js: CITY_TARIFF` — 그 도시만의 **오버라이드**. 관세가 도시 성격의 일부인 항구에만 적는다.
  적으면 `content/regions/<권역>-evidence.json`의 `cities[id].tariff`에 근거도 적어야 하고,
  `check-evidence.mjs`가 불일치·유령·**배선끊김**을 실패시킨다. 어디에 몇 %인지도 그 스크립트가 출력한다.

읽는 함수가 둘이라 헷갈리기 쉽다 — 항구의 **성질**을 적는 자리(표·검증)는 `baseTariff()`,
지금 실제로 무는 값은 `tariffRate()`(부관 특전이 곱해진다). 대시보드 **항구** 탭이 둘을 나란히 보여준다.

(밀무역·면세 특권은 뒷날의 확장 자리)

## 차익 구조 예시

기준가는 **곡물 20닢을 앵커로 한 사료 비율**이다(향신료 ×16.5 · 비단 ×21 · 금괴 ×35).
품목별 실제 값과 배율은 `data.js: GOODS`가 정본이고 대시보드 **보수·물가** 탭이 그때그때 표로 낸다 —
여기 옮겨 적으면 물가를 조정할 때마다 낡는다(실제로 낡았던 자리다).

고가품일수록 산지·수요지 배율이 낮다 — 자본이 커지면 회전율보다 물량이 중요해지도록.
**실효 배율에서 다시 시장 깊이와 입항세가 깎인다.** 화물칸을 가득 채운 한 방은 표의 배율만큼 벌지 못한다.

**의도한 장거리 항로:** 베이루트 향신료 → 베네치아 / 이스탄불 비단 → 제노바 / 알렉산드리아 곡물 → 튀니스.
멀수록 유지비와 해적 조우 횟수가 늘어 위험이 커진다.

## 매매

```js
buy(goodId, qty)   // → {ok, qty, cost, unit} | {ok:false, reason}
sell(goodId, qty)  // → {ok, qty, gain, unit, profit}
```
- 매입 수량은 `min(요청, 화물 여유, floor(gold/unit))`로 자동 클램프. 실패가 아니라 **가능한 만큼** 산다.
- `state.buyPrice[id]`에 **가중평균 매입가**를 유지해 시장 화면에 손익을 표시한다.
  `(기존평균×보유 + 이번비용) / 총수량`
- 전량 매도 시 `cargo`와 `buyPrice` 항목을 함께 삭제한다(잔여 0 항목이 UI에 남지 않게).
- UI 조작: 기본 10개 / `Shift` 전량 / `Ctrl` 1개 (`port.js`의 클릭 핸들러가 `e.shiftKey` 검사)

## 바람과 해류 — 어디로 가느냐가 일수를 가른다

```js
voyageDays(a,b) = max(1, round(거리 / (13 × shipSpeed() × routeFactor(a,b))))
routeFactor     = windFactor × currentFactor
```

- **바람**: 계절풍(1년 120일). 여름엔 북풍이 남으로, 겨울엔 남서풍이 북동으로 민다. 3일마다 ±30° 흔들린다(시세와 같은 리듬).
- **돛**: `SHIPS[].rig`(스퀘어 비율 0~1). 순풍 이득은 `align × (0.16 + rig×0.20)`, 역풍 손해는 `align × (0.30 − (1−rig)×0.16)`.
  → **카라벨(라틴세일 rig 0)은 역풍에 강하고, 프리깃(가로돛 rig 1)은 순풍에 강하다.**
- **해류**: `CURRENTS`에 실린 구간만. 지중해는 아프리카 연안을 동진해 레반트에서 북상한다.
- 결과적으로 **왕복이 비대칭**이다 — 베네치아→이스탄불 7일인데 돌아올 땐 12일이 되기도 한다.
  항로 목록에 순풍/역풍과 일수·비용을 함께 띄워 미리 판단할 수 있게 했다.

⚠️ `rig`는 `data.js: SHIPS`(항해 성능)와 `sprites/ship.js: HULLS[].masts[].sail`(그림)에 **따로** 있다. 선종을 손보면 둘 다 고친다.

## 시간과 비용

```js
일당       = round(crew × avgCrewWage() × days)      // 술집에서 누구를 태웠나로 갈린다(기본 1.2)
보급       = round(crew × SUPPLY_UNIT(1.3) × days)     // 식량과 물
선체 유지   = round(SHIPS[].upkeep × HULL_UPKEEP(1.0) × days)   // 기함. 배가 클수록
무장 유지   = round(armsUpkeep() × days)               // 대포 1문당 경0.5·중0.9·장1.6
선단 유지비 = fleetUpkeep() × days                     // 정박 중인 다른 배들
적하보험    = round(화물가치 × 항로요율(%) × INSURANCE_RATE(0.3))  // 값나가는 짐 × 위험한 구간
부관 급여   = round(OFFICER.wage(2.6) × days)
누수       = ship.leak × days                         // 낡은 바사만 (선체가 삭는다)
```
`advanceDays(n, {from, to})`가 위 항목 전부와 `{leak, expired, total}`을 돌려주고 `map.js: arrive()`가 항해일지에 적는다.
**갈래를 나눈 이유**는 뭉뚱그리면 "왜 돈이 안 모이나"를 플레이어가 읽을 수 없기 때문이다.

★ **`total`은 견적이지 그날 금고에서 빠진 액수가 아니다.** 일당과 부관 급여는 **쌓이기만 하고**
(`state.payroll.due`) 30일마다 항구에서 치른다 — 즉시 나가는 것은 보급·선체·무장·선단·보험뿐이다.
못 주면 사람이 짐을 들고 떠난다. → [payroll.md](payroll.md)

**★ 임금은 사료 대비 과중했다.** "선원 연봉으로 배를 몇 척 사나"로 재면 게임 11배 : 사료 30배였다
(→ `content/asset-evidence.json`: 임금 대비 배값). 그래서 일당을 2.4→1.2, 부관 급여를 16→2.6으로 내리고,
줄어든 압박을 **성장할수록만 무거워지는 갈래**(선체·무장·보험)로 옮겼다.
항해비 구성비(어느 갈래가 얼마를 먹나)는 대시보드 **보수** 탭이 그때그때 계산해 보여준다 —
콘텐츠·밸런스가 바뀌면 곧바로 달라지는 값이라 여기 적어 두지 않는다.

**적하보험이 성장 브레이크다.** 요율은 `map/geo.js: ROUTE_RISK`(당대 해상보험 2~9%)를 그대로 쓴다 —
초반엔 곡물·소금을 이웃 항구로 나르니 거의 0이고, 향신료·비단을 먼 구간으로 나르기 시작하면 급격히 는다.
같은 사실의 반대편이 `state.js: cargoLure`로, **화물이 값나갈수록 해적 조우 확률도 오른다**(9,000닢당 +5%p, 상한 +14%p).

`node tools/sim-trade.mjs`(최적 플레이·다품목·NPC 포함, 계약과 전리품은 제외) 기준:

|---|---|---|---|---|---|---|

## 초기 조건

금화 **200** / **낡은 바사**(선체 55·화물 45·경포 2문) / **선원 0명** / 베네치아 정박 (`resetGame()`)

**갑판이 비어 있다.** 배는 있는데 몰 사람이 없으므로 첫 행동은 매매가 아니라 **술집행**이다
(→ [crew-tavern.md](crew-tavern.md)). 낡은 바사는 최소 5명이 필요하고, 계약금 8닢/명 안팎이라
다섯을 태우는 데 40~60닢이 든다 — 시작 금화의 3분의 1이다.

물이 새는 배라 오래 못 탄다. 첫 목표는 **제대로 된 배를 사는 것** — 가까운 제노바(플류트 2,600)나
베네치아 자체(캐랙 9,800)가 후보다. 베네치아 비단·유리세공을 이웃 항구에 넘기는 짧은 왕복이 초반 루프.

시작 자금이 900→200으로 내려가면서 초반이 크게 느려졌다. **급여는 월말 정산**이라
(→ [payroll.md](payroll.md)) 첫 30일은 물자·유지비만 나가고 그 달 말에 삯이 한꺼번에 닥친다.
150닢으로는 30항차 12판 중 **1판만 완주**했다 — 매입 자본이 100닢 남짓이라 한 항차 이익이
항해비를 못 넘는다. 200닢이 "대체로 굴러가지만 한 번 삐끗하면 삯이 밀리는" 구간이다(8/12 완주).
