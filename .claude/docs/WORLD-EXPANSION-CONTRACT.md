# 세계 확장 계약서 — 권역 담당자가 읽는 문서

> tradeship을 지중해 한 바다에서 **전 세계**로 넓히는 작업의 규약이다.
> 담당자(사람이든 에이전트든)는 **이 문서 하나만 읽고** 자기 권역을 채울 수 있어야 한다.
> 게임 코드를 통째로 읽을 필요는 없다. 다만 아래 §0의 원칙은 협상 대상이 아니다.

---

## 0. 절대 원칙 (프로젝트 최상위 지침)

### 0-1. 콘텐츠는 풍부하게, 금액은 근거에 충실하게

- **콘텐츠**(배·교역품·도시·해적·인물의 *종류*)는 **많을수록 좋다.**
  근거가 아직 없다는 이유로 항목을 빼지 않는다 — **먼저 넣고 근거는 뒤따른다.**
  검증 스크립트는 "근거 없음"을 **경고**로만 잡는다(실패가 아니다). 그렇게 설계돼 있다.
- **금액·시세**(값·비율·위험도)는 사료에 충실해야 한다. **돈은 어렵게 벌려야 재미가 있다.**
  수익이 후해 보이면 근거부터 확인하고, 근거가 아니라 편의면 올리지 않는다.

### 0-2. 연도를 고정하지 않는다

배경은 "대항해시대쯤"이다. 특정 해에 맞추면 그 해에 없던 도시·세력·선종을 계속 덜어내야 한다.
**콘텐츠가 풍성한 쪽을 택한다 — 이왕이면 모두 나오게 한다.**
실제로 공존하지 않은 것이 한 화면에 있어도 된다(기사단령 로도스 ↔ 기사단령 몰타가 그 예다).
그런 항목은 근거 JSON에 `"verdict": "gameplay"`로 적어 **알고 그렇게 뒀다**는 것을 남긴다.
개별 사실의 고증(무엇이 어디서 났나, 어느 항로가 위험했나)은 여전히 사료를 따른다.

### 0-3. 조사 → 데이터 → 코드, 그리고 그 셋이 어긋나면 기계가 실패시킨다

이 프로젝트의 데이터는 **세 겹**이다. 어느 하나만 고치면 검증이 실패한다.

| 겹 | 무엇 | 어디 |
|---|---|---|
| ① UI | 좌표·깃발·규모·공업력 | `js/regions/<권역>/geo.js` |
| ② 수치 | 산지/수요 배율·값·위험도 | `js/regions/<권역>/geo.js`·`trade.js`·`goods.js`·`ships.js` |
| ③ 근거 | 왜 그 값인가 + 출처 | `content/regions/<권역>-evidence.json` |

**수치를 적었으면 근거도 같은 작업에서 적는다.**

## 1. 네가 건드리는 파일 (이것 말고는 손대지 않는다)

권역 담당자는 **자기 권역 폴더와 자기 근거 파일만** 건드린다.
다른 권역, `js/data.js`, `js/state.js`, `js/regions/index.js`, 대시보드, 검증 스크립트는
**절대 수정하지 않는다.** 여럿이 동시에 일하므로 공용 파일을 건드리면 남의 작업을 덮어쓴다.

```
js/regions/<권역>/geo.js       도시·항로·위험도·해류          ← 권역 담당
js/regions/<권역>/trade.js     산지/수요 배율 + 입항세         ← 권역 담당
js/regions/<권역>/goods.js     이 권역이 처음 들여오는 교역품   ← 권역 담당
js/regions/<권역>/ships.js     이 권역에서 짓는 선종           ← 권역 담당
content/regions/<권역>-evidence.json   위 넷의 근거            ← 권역 담당

js/regions/<권역>/npc-traders.js   무역상                     ← 무역상 담당
js/regions/<권역>/npc-pirates.js   해적                       ← 해적 담당
js/regions/<권역>/npc-figures.js   항구 인물                  ← 인물 담당
```

NPC 담당자는 **모든 권역의 자기 파일**(`npc-traders.js` 7개 등)을 건드리고,
권역 담당자는 **자기 권역의 나머지 파일**을 건드린다. 그래서 서로 부딪히지 않는다.

**근거 파일은 권역 담당자가 소유한다.** NPC 담당자는 근거 파일을 직접 고치지 말고,
자기가 만든 인물·해적·상단의 사료 출처를 **보고서에 적어** 넘긴다(통합자가 합친다).

## 2. 좌표 규칙 (geo.js)

권역마다 **자기 400×225 좌표계**를 쓴다. 지중해의 (141,63)과 인도양의 (141,63)은
아무 관계가 없다. 그러니 실제 위경도를 옮기려 애쓰지 말고 **놀기 좋은 도식**으로 그린다.

- **x는 8~392, y는 20~205** 안에 둔다(가장자리는 지도 그림의 여백이다).
- **도시 사이는 12px 이상** 떨어뜨린다 — 클릭 판정이 반경 6px이라 겹치면 못 고른다.
- **이름표가 겹치지 않게 한다.** 이름표는 도시 **위쪽**에 배경 박스째 그려지고,
  폭은 한글 글자당 약 6px이다("캘리컷"이면 약 24px). 이웃 도시의 표식을 덮지 않는지
  좌표를 정하고 나서 **계산해 본다**(실제로 부르사·이즈니크에서 4건이 겹친 적 있다).
- 항로가 지나는 자리를 생각해 배치한다. 지도 그림은 나중에 이 좌표를 **기준판** 삼아 그린다 —
  즉 **좌표가 먼저고 지형이 나중이다.** 지형에 맞추려 좌표를 비틀지 않는다.
- 내륙 도시를 넣어도 된다(부르사가 그렇다). 그때는 관문 항구에서만 이어 **막다른 주머니**로 둔다.

### 항로(ROUTES)

- 권역 **안**의 연결만 적는다. 다른 권역으로 나가는 선은 `js/regions/index.js: OCEAN_LANES`에
  이미 있다(공용 파일이라 담당자가 고치지 않는다 — 필요하면 보고서에 적는다).
- **`OCEAN_LANES`가 요구하는 관문 항구는 반드시 그 id로 만든다.** 아래 §7 표를 볼 것.
- 그래프가 이어져 있어야 한다. 고립된 도시는 아무도 안 간다.
- 한 도시의 이웃은 2~5개가 적당하다. 다 이으면 지도가 거미줄이 되고 선택이 사라진다.

### 위험도(ROUTE_RISK) — **당대 해상보험 요율(%)**

추정치가 아니라 **당대인이 돈을 걸고 매긴 값**을 쓴다. 지중해의 앵커는 이렇다:

| 요율 | 성격 | 예 |
|---|---|---|
| 2.0~3.5 | 한 세력의 내해, 아군 해안이 늘 가깝다 | 나폴리~베네치아 2.0 |
| 4.0~5.5 | 평범한 연안 항로 | 아테네~이스탄불 4.0 |
| 6.0~8.0 | 외해·깃발이 적대·병목 통과 | 알렉산드리아 편도 6.0 · 에게해 8.0 |
| 9.0~11.0 | 사략 소굴 앞·며칠씩 뭍이 안 보임 | 바르셀로나~알제 9.0 · 희망봉 11.0 |

- 요율을 가르는 것은 **(내해/외해) × (양단 깃발의 적대) × (아군 해안까지의 거리)**다.
  교통량은 변수가 아니다(지중해 조사에서 확인된 결론).
- `null`로 두면 그 구간은 **해적이 안 나온다**(내해·강·육로). 대신 뭍의 사고(노상강도·통행세)가 난다.
- 이 값은 **두 곳에서 쓰인다** — 해적 조우 확률과 **적하보험료**다. 올리면 위험만 커지는 게
  아니라 후반 비용 구조가 함께 움직인다.

## 3. 경제 규칙 (trade.js)

```js
export const TRADE = {
  calicut: {
    supply: { pepper: 0.46, ginger: 0.60 },   // 산지라 싸다 (배율 < 1)
    demand: { silver: 1.34, weapon: 1.30 },   // 수요지라 비싸다 (배율 > 1)
    blurb: '후추가 나는 말라바르의 관문. 사무티리가 다스린다.',
  },
};
```

- **배율 폭**: supply는 `0.44~0.78`, demand는 `1.18~1.46`. 이 밖으로 나가면 차익이 튀어
  경제가 그 항구로 쏠린다(`SPREAD` 계수가 폭을 조이지만 한계가 있다).
- 한 도시에 **supply 1~3개 · demand 2~4개**가 적당하다. 다 채우면 그 항구가 만능이 된다.
- ★ **품목마다 산지와 수요지가 둘 다 있어야 죽지 않는다.** 네 권역이 새 품목을 만들었다면
  그 권역 안에 **파는 곳과 사는 곳을 모두** 둔다. 산지만 있으면 중립가로만 팔리고,
  수요만 있으면 그 칸은 아예 죽는다.
- **같은 도시에 같은 품목을 supply와 demand 양쪽에 넣지 않는다**(뒤엣것만 남는다).
- `blurb`는 한 줄. 그 항구가 무엇으로 먹고사는지가 읽혀야 한다.

### 입항세 오버라이드

`TARIFF_OVERRIDE`는 **관세가 그 도시 성격의 일부인 곳만** 적는다. 비워 두면 규모별
기본율(size 1→3% · 2→4.5% · 3→6%)로 굴러간다 — **여기 없는 도시가 "빠진 것"이 아니다.**
사료가 20%라 해도 게임은 **매각에만** 물어 그대로 옮기면 그 항구가 통째로 죽는다.
성격이 드러날 만큼만 올리고(대략 3~9%) `verdict: "gameplay"`로 남긴다.

## 4. 교역품 (goods.js)

```js
export const GOODS = [
  { id: 'clove', name: '정향', base: 520, icon: 'spice', bulk: 1 },
];
```

- ★ **id는 세계에서 하나뿐이다.** 이미 다른 권역이 정의한 품목을 다시 적지 않는다.
  **이미 있는 12종**: `grain`(곡물 20) `salt`(소금 48) `wine`(와인 38) `oliveoil`(올리브유 52)
  `ceramic`(도자기 130) `weapon`(무기 165) `fur`(모피 175) `glass`(유리세공 190)
  `ivory`(상아 300) `spice`(향신료 330) `silk`(비단 420) `gold`(금괴 700).
  "우리 권역에서도 난다"는 goods가 아니라 **trade.js의 supply**로 적는 것이다.
- **base는 곡물 20닢 대비 사료 비율**로 정한다. 감으로 매기지 않는다.
  참고: 향신료 ×16.5 · 비단 ×21 · 금괴 ×35. 새 품목도 "곡물의 몇 배였나"를 조사해 정한다.
- `icon`은 `js/sprites/icons.js`의 키여야 그림이 뜬다. **새 아이콘은 아직 없다** —
  가장 가까운 기존 키를 빌려 쓰고(정향→`spice`, 면포→`silk`), 근거 JSON의
  `art.iconTodo`에 "무엇을 그려야 하는지"를 적어 둔다.
- 권역당 **5~12종**이 적당하다. 너무 잘게 가르면(후추/정향/육두구/메이스/계피…) 화면에서
  구별이 안 되고, 너무 뭉치면 그 바다의 성격이 사라진다.

## 5. 선박 (ships.js)

```js
export const SHIPS = {
  nau: {
    hull: 'carrack', name: '나우', origin: '포르투갈', originFlag: 'portugal',
    tier: 2, era: 'classic', requires: null, yards: ['lisboa'], price: 11000,
    hp: 200, crew: 50, crewMax: 80, crewMin: 32, cargo: 260, guns: 16, speed: 1.00,
    upkeep: 24, rig: 0.67, tint: 'oak',
    desc: '인도 항로를 오가던 대형 상선. 짐을 많이 싣고 파도를 잘 견딘다.',
  },
};
```

- ★ 키는 **세계에서 하나뿐**이다. 이미 있는 11종: `hulk cocca galley caravel fluyt brig
  carrack frigate galleon indiaman superfrigate`.
- `hull`은 `js/sprites/ship.js: HULLS`의 키여야 그림이 뜬다. **쓸 수 있는 것**:
  `hulk caravel galley fluyt brig carrack frigate galleon indiaman superfrigate`.
  그 바다 고유의 선형(정크·다우·프라우·갤리어스…)이 필요하면 **가장 가까운 것**을 쓰고
  근거 JSON의 `art.hullTodo`에 "어떤 배이고 무엇이 달라야 하는지"를 적는다.
- `originFlag`를 단 항구는 **요구 공업력이 1 낮다**("제 나라 배는 짓기 쉽다").
  깃발 키는 `js/sprites/ship.js: FLAGS`에 있어야 한다. **쓸 수 있는 것**:
  `venice genoa spain ottoman france england pirate hospitaller hafsid`.
  새 깃발이 필요하면(포르투갈·명·조선·마자파힛…) 가장 가까운 것을 쓰고
  근거 JSON의 `art.flagTodo`에 적는다.
- **값 사다리**(이 밖으로 나가면 경제가 무너진다):

  | 급 | 정가 | 화물칸 | 예 |
  |---|---|---|---|
  | 첫 배 | 1,100~1,400 | 78~90 | 코카·카라벨 |
  | 중형 | 2,100~4,200 | 58~170 | 갤리·플류트·브리간틴 |
  | 대형 상선 | 9,800~14,000 | 110~240 | 캐랙·갈레아스 |
  | 최상급 | 19,500~42,000 | 150~320 | 갈레온·아르고시·대형 갈레온 |

- `rig`(가로돛 비율)는 **그림의 돛과 같이 가야 한다.** 라틴세일·정크세일 위주면 0.0~0.3.
- `crewMin`은 그 배의 정체성이다. **화물톤 ÷ 승조원 1인**이 사료 밴드에 들어야 한다
  (지중해 기준: 갤리 1.2 · 코카 13 · 플류트 18.9). 다우·정크는 이 값이 높은 쪽이다.
- 권역당 **3~8종**. `tier 0`은 시중에 안 나온다(적 전용).

## 6. 근거 JSON (`content/regions/<권역>-evidence.json`)

이미 틀이 있다. `cities` `routes` `goods` `ships` 네 절을 채운다.
판정 라벨·시대 전제는 `content/evidence-meta.json`이 정본이므로 **여기 다시 적지 않는다.**

```jsonc
{
  "cities": {
    "calicut": {
      "flag": { "value": "ottoman", "verdict": "gameplay",
                "basis": "사무티리의 깃발이 FLAGS에 아직 없어 가장 가까운 것을 빌렸다. art.flagTodo 참조." },
      "tariff": { "value": 0.06, "verdict": "confirmed",
                  "basis": "…40자 이상, 무엇을 근거로 이 값인지가 한 문장으로 읽혀야 한다…",
                  "sources": [{ "title": "…", "url": "…" }] },
      "goods": {
        "pepper": { "side": "supply", "value": 0.46, "verdict": "confirmed",
                    "basis": "…", "sources": [{ "title": "…", "url": "…" }] }
      }
    }
  },
  "routes": {
    "calicut|cochin": { "risk": 4.0, "verdict": "probable", "basis": "…", "sources": [] }
  },
  "goods": {
    "clove": { "base": 520, "verdict": "confirmed", "basis": "곡물의 몇 배였는지…", "sources": [] }
  },
  "ships": {
    "nau": { "price": 11000, "verdict": "probable", "basis": "…", "sources": [] }
  },
  "art": {
    "iconTodo": [{ "good": "clove", "note": "말린 꽃봉오리 다발 — 지금은 spice 아이콘을 빌려 쓴다" }],
    "hullTodo": [{ "ship": "junk", "note": "정크 — 격벽 선체에 부채꼴 정크세일 3장" }],
    "flagTodo": [{ "key": "portugal", "note": "흰 바탕 파란 십자 + 성곽 테두리" }],
    "styleTodo": [{ "key": "swahili", "note": "산호석 벽·평지붕·모스크 첨탑" }]
  },
  "openQuestions": ["아직 못 밝힌 것"]
}
```

**판정(verdict) 고르는 법** — 이게 이 프로젝트의 정직성 장치다:

| 값 | 뜻 | 조건 |
|---|---|---|
| `confirmed` | 사료로 확인됨 | **출처가 반드시 있어야 한다**(없으면 검증 실패) |
| `corrected` | 조사로 바로잡음 | 같음 — 출처 필수 |
| `probable` | 개연성 있음 | 직접 근거는 약하다. 출처가 없어도 된다 |
| `gameplay` | 게임을 위해 고증을 덮어씀 | 알고 그랬다는 표시 |

- ★ **출처를 못 찾았으면 `probable`로 내리는 것이 정직한 처리다.** `confirmed`를 달고
  출처를 비우면 다음 사람이 "검증된 값이구나" 하고 지나간다 — 검증이 이것을 실패로 잡는다.
- `basis`는 **40자 이상**, 한 문장으로 읽혀야 한다. "무엇을 근거로 이 값인가"가 답이다.
- 출처는 실제로 존재하는 것만 적는다. **URL을 지어내지 않는다.**
  찾지 못했으면 `sources`를 비우고 `probable`로 둔다.

## 8. 다 하고 나서 — 검증

담당자는 아래를 **직접 돌려 통과시킨 뒤** 보고한다. 실패한 채로 넘기지 않는다.

```bash
node -e "import('./js/data.js').then(m=>console.log(m.CITIES.length, m.GOODS.length, Object.keys(m.SHIPS).length))"
node tools/check-evidence.mjs      # 도시 수치 ↔ 근거
node tools/check-routes.mjs        # 항로 요율 ↔ 근거
node tools/test-rules.mjs          # 규칙이 안 깨졌나
node tools/test-world.mjs          # 세계가 굴러가나
```

- **경고(soft)는 통과다.** "아직 근거가 없다"는 경고일 뿐 실패가 아니다.
- **실패(exit 1)는 반드시 고친다.** 대개 원인은 셋이다:
  코드와 근거의 값이 다르다 · 근거에만 있고 코드엔 없다(유령) · `confirmed`인데 출처가 없다.
- 문법 오류는 `node -e "import('./js/regions/<권역>/geo.js')"`로 먼저 잡는다.

## 9. 보고서에 적을 것

1. 만든 것의 수 — 도시 N · 항로 N · 교역품 N · 선종 N
2. **그 바다의 성격을 한 문단으로** — 무엇으로 먹고사는 바다이고 무엇이 위험한가
3. 근거를 못 찾아 `probable`로 둔 것들
4. `art.*Todo`에 적은 것 — 그림 담당이 알아야 할 새 아이콘·선형·깃발·화풍
5. 공용 파일에 넣었으면 하는 것(원양 항로 추가 등) — **직접 고치지 말고 여기 적는다**
